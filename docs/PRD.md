# 逐字稿提取器 · 产品需求文档（V1）

> 产品形态：Web 工具
> 核心原则：先把「音视频 / 链接 → 逐字稿 → 导出」这条闭环做扎实，再扩展平台与上线能力。
> 说明：这是公开版本的产品文档，只保留产品设计与验收相关内容；开发过程记录不在此文档内。

---

## 一、产品背景

在学习、内容研究、播客整理、视频资料分析等场景里，把一段音视频变成可编辑、可保存、可继续分析的逐字稿，是一件高频但麻烦的事：

- 平台视频自带字幕，但用户很难方便地导出；
- 没有字幕的视频，需要先下载、再单独找工具做语音转写；
- 不同平台、不同内容形态的处理方式不同，操作分散；
- 转写完成后往往还要自己整理成 Markdown 或 TXT；
- 对非技术用户来说，这一串步骤门槛偏高。

V1 的目标是把这条流程收敛成一个工具：

> **用户给出一个本地音视频文件或一个视频链接，系统自动选择处理路径，输出可下载的逐字稿。**

---

## 二、目标用户

**主要用户**

- 需要整理视频、播客、课程内容的个人用户；
- 内容创作者、研究者、学生；
- 需要把音视频内容进一步交给 AI 做摘要、提炼、分析的人。

**核心场景**

1. 拿到一条 B 站视频链接，想直接得到逐字稿；
2. 手上有本地 MP3 / M4A / WAV / MP4 / MOV 文件，想快速转写；
3. 转写结果要继续喂给其它 AI 工具做摘要、观点提取、知识沉淀。

---

## 三、V1 核心目标

V1 只验证一件事：**用户能否从「提供内容」一路走到「拿到并下载逐字稿」。**

成功标准（7 条）：

1. 能处理本地音频与视频；
2. 能处理 B 站视频链接；
3. B 站有字幕时优先提取字幕；
4. 无字幕时自动取音频并语音转写；
5. 页面上能看到处理结果；
6. 能导出 Markdown 与 TXT；
7. 失败时用户能看到明确原因，并知道下一步怎么做。

## 四、范围

### 4.1 V1 必须包含

**输入方式 A：本地文件**（MP3 / M4A / WAV / MP4 / MOV）

```text
上传文件 → 识别类型 → 视频先提取音频 → 语音转写 → 生成逐字稿 → 页面预览 → 导出 Markdown / TXT
```

**输入方式 B：B 站链接**

```text
粘贴链接 → 解析视频信息 → 检查字幕
  ├─ 有可用字幕 → 提取字幕
  └─ 无可用字幕 → 取音频 → 语音转写
→ 标准化为逐字稿 → 页面预览 → 导出 Markdown / TXT
```

**长任务相关（V1 内）**：处理过程要可见、可中断、失败不白跑 —— 见第五节。

### 4.2 V1 明确不做

| 不做 | 原因 |
| --- | --- |
| 抖音 / 小红书 / YouTube 链接 | 平台解析难度与合规风险差异大；V1 先把一条链路做透 |
| 画面烧录字幕（硬字幕）OCR | 与「字幕提取」不是同一能力，需要独立的 OCR 链路 |
| 多 P / 合集 / 播放列表 | 一个任务产出多份逐字稿会改变任务与产物结构，需求待验证 |
| 多文件批量上传、批量任务 | 并发与队列是上线阶段的问题，不是 V1 的验证目标 |
| 说话人识别、翻译、LLM 清洗（去口头禅、错字纠正、智能分段） | 都属于「逐字稿之后的加工」，会稀释 V1 的验证重点 |
| 自动摘要 / 观点提取 / 章节划分 | 同上 |
| 账号体系、历史任务中心、邀请码 | 单用户本地工具阶段不需要 |
| 云对象存储、RAG、向量库 | 上线阶段再评估 |

判断标准只有一条：**它是否影响「内容 → 逐字稿 → 导出」这条闭环的成立。** 不影响就不进 V1。

## 五、长任务体验设计

转写是耗时操作（CPU 上约 2–4 倍实时，1 小时内容约需 15–30 分钟）。
「一次性等结果」的体验不可接受，因此 V1 明确要求：

| 要求 | 设计说明 |
| --- | --- |
| **过程可见** | 逐段产出即时出现在页面上；显示精确百分比（已转写时长 / 总时长）与已生成段数 |
| **首字延迟有交代** | 模型加载、音频分析期间没有任何文字可展示，必须给独立文案（如「正在加载语音识别模型」），不能静默等待 |
| **刷新不丢** | 已生成内容落盘；刷新页面后重放内容与刷新前一致，并继续增量更新 |
| **中断可续** | 服务被强杀/重启后，有进度的任务从断点续写，不重跑已完成部分 |
| **可控** | 用户可取消任务；取消立即生效，已生成内容保留 |
| **失败不白跑** | 失败时保留已生成片段，明确标注「未完成」并给出下一步 |
| **不产生半成品** | 失败或取消的任务**不生成** Markdown / TXT / 结构化结果文件 —— 避免半成品被当成完整逐字稿使用或传播 |

## 六、处理逻辑与路由规则

V1 采用**确定性工作流**，不把固定流程交给大模型临时判断：

```text
输入
├─ 本地文件
│  ├─ 音频 → 直接转写
│  └─ 视频 → 提取音频 → 转写
└─ B 站链接
   ├─ 有可用字幕（人工字幕优先于 AI 字幕）→ 提取字幕
   └─ 无可用字幕 → 只下载音频轨 → 转写
```

规则：

1. 优先使用已有字幕，只有没有可用字幕时才调用语音识别（成本与耗时差两个数量级）；
2. 字幕获取失败**不等于任务失败**，自动降级为语音转写；
3. 失败不无限重试；
4. 链接解析失败时，引导用户改用本地文件上传；
5. 每一步都由确定性代码控制，可测试、可预测、可解释。

## 七、任务状态与用户可见文案

长任务不使用「单次请求一直等待」。状态机：

```text
本地音频：pending → validating → transcribing → exporting → succeeded
本地视频：pending → validating → extracting_audio → transcribing → exporting → succeeded
B站有字幕：pending → checking_subtitle → exporting → succeeded
B站无字幕：pending → checking_subtitle → downloading_audio → transcribing → exporting → succeeded
任何非终态 → failed（失败）或 cancelled（用户取消）
```

界面展示的是**产品语言**，不是状态码：

- 正在检查视频字幕 / 未发现可用字幕，正在下载音频
- 正在加载语音识别模型 / 正在生成逐字稿（已生成 128 段）
- 逐字稿已生成 / 任务未完成 / 任务已取消

---

## 八、输出内容

**页面**：标题、来源、处理方式（字幕提取 / 语音转写）、逐字稿正文（带时间戳、可复制全文）、下载入口。

**Markdown**（适合继续加工）：

```markdown
# 视频标题

- 来源：Bilibili / 本地文件
- 原始地址：
- 处理方式：字幕提取 / 语音转写
- 生成时间：

## Transcript

[00:00:00] 正文内容……
[00:00:30] 正文内容……
```

**TXT**：只保留可读文本与时间戳，方便直接阅读或粘进其它工具。

## 九、异常与降级（用户看到什么）

| 情况 | 用户看到的 |
| --- | --- |
| 链接解析失败 | 当前链接解析失败。你可以重试，或将视频/音频保存到本地后直接上传。 |
| 无字幕且音频获取失败 | 未能提取该视频的音频，建议改用本地文件上传。 |
| 内容里没有人声（静音 / 纯音乐） | 未在文件中检测到人声。请确认文件是否正确，或更换包含人声的文件后重试。 |
| 文件不包含音轨 | 该文件不包含音轨，无法生成逐字稿。请确认文件是否正确。 |
| 不支持的格式 | 提交前直接提示支持格式，不创建任务 |
| 超过时长上限 | 在下载前判断并提示，不浪费流量 |
| 会员专享 / 只能拿到预览片段 | 明确失败，提示原因，**不允许用预览片段冒充完整逐字稿** |
| 转写失败 | 转写未完成，请重试。原始文件不会被修改 |

两条硬规则：

1. 所有用户可见文案**纯中文**，不出现错误码、程序堆栈、英文状态名、技术术语；
2. 每条错误都必须告诉用户**下一步怎么办**（重试 / 改用本地上传 / 分段处理）。

## 十、非功能要求

### 10.1 安全

- 密钥、登录凭据只存在于服务端环境变量，不进入前端、不进入版本控制；
- 上传文件名做安全处理，服务端校验真实文件类型；
- 错误信息不展示程序堆栈；
- 日志不记录完整音视频内容、逐字稿正文与凭据。

### 10.2 可恢复性

- 长任务状态不得只存在于进程内存；
- 服务重启后仍能查询任务；有进度的任务能从断点续写；
- 失败与取消都要落到明确的终态，并可查到原因。

### 10.3 可验证性

每个能力都必须能用**真实验收**证明，而不是只有单元测试：

- 自动化测试（后端接口与状态机、前端组件与接口契约）；
- 真实本地音频、真实本地视频；
- 真实 B 站「有字幕」与「无字幕」链接；
- 错误路径（无声内容、无音轨、不支持格式、超限）；
- 长内容实测（≥1 小时）与中断恢复实测。

## 十一、关于 Skill 的定位

项目包含一个独立 Skill 文档，用来描述「如何完成逐字稿提取任务」：输入判断、字幕优先策略、转写降级、失败处理、输出格式。

边界很明确：

- Skill **不**提供下载能力、**不**替代后端代码、**不**替代 yt-dlp / FFmpeg / faster-whisper；
- **产品运行不依赖任何大模型 API** —— 不加载任何 LLM 也能完成核心任务。

这是刻意的选择：核心链路的确定性比"看起来智能"更重要。

## 十四、V1 成功定义

V1 不以「支持平台最多」「页面最漂亮」或「用了 Agent」作为成功标准。

V1 成功只看：

> **一个非技术用户，能否通过一个简单页面，把本地音视频或 B 站视频稳定地变成可下载的逐字稿。**
